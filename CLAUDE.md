# Portfolio agent

A personal portfolio tracker that runs only on this Mac. Playwright signs in to bank and brokerage portals. A local Qwen model (no cloud LLM) reads the captured pages. Values go into an append-only SQLite store, and a local FastAPI dashboard shows them. `docs/spec.md` is the spec to build against, and `docs/design/` holds the earlier design checkpoints.

## Privacy and security rules (always)

- **Never read** `data/private/**`, `.env`, `.env.*` or any `*.db` file. They hold credentials, captured portal pages and real balances. Inspect data through the dashboard API instead, which returns only what the UI shows.
- **What you read is sent to Anthropic, so read as little real data as possible.** Everything a tool returns, including dashboard API responses, goes to the model's servers. When checking the owner's real data, print only IDs, counts, dates, statuses and yes/no checks. Never print names, account titles, account numbers (not even last 4), file names (they often contain account numbers), balances, totals, holdings or prices. Filter in the command (e.g. `python3 -c` that prints `len(...)` or `x == y`), not after seeing the output. Never extract text from the owner's statements or pages to read it, not even masked; ask the owner to describe the layout or share a sample with made-up values instead.
- **Never put real data in code, tests, docs or commits.** That covers account numbers (including masked last-4 digits), balances, holdings, and the names of family members or accounts. Tests use made-up values such as "Alex", "Kid - 529" and "…1234". Check `git diff` for these before every commit.
- **Never log, trace or send to the model** passwords, usernames or verification codes. Traces are shown in the Debug tab.
- **Nothing leaves the machine.** No outside services, telemetry or cloud APIs for portfolio data. One exception, chosen by the owner: `email_codes.py` signs in to Gmail over IMAP (app password, encrypted in `app_secrets`) to read emailed verification codes. It only reads (mailbox opened read-only, `BODY.PEEK`), only messages that arrived after the code was requested and come from the login's domains or its `code_sender`, and never logs, traces or stores a code or message text. Never widen what it reads.
- **The owner signs in to portals.** Don't start a Refresh on their behalf without asking; it signs in to their bank.

## Working with the owner

- **Ask before committing or pushing.** Work happens on feature branches, not `main`.
- **Apply settings to their real login, not just the form.** When a request is about their own accounts (for example "ignore Investments on Bank of America"), build the feature, then set it on their live login through the API, check that it took effect on existing accounts, and say what was set.
- **Explain changes in plain terms:** what they'll see and what they need to do. Name any limitation that wasn't verified against the real portal.

- **Refresh supported** (`refresh_supported`) is not a setting: it is true for every login whose access method is Browser (`registry._login_extras`; `save_login` keeps the old `holds_public` column in step). Those logins get a Refresh button (Accounts & logins), are part of the Dashboard's Refresh, and can be refreshed through the API; every other login shows **Upload statements**. Access methods API, Email statement and Manual are shown greyed out and refused (`registry.PLANNED_ACCESS`) until built. Removed options: field selectors, documents filter, fund links, 2FA "authenticator", account types "wealth management" and "other". A login's "Closed on" shows only when its status is Closed.

- **Daily Refresh** (`schedule.py`): `serve` (`create_app(scheduler=True)`; tests and demos built with `create_app` don't schedule) checks every 30 s and starts the Dashboard's Refresh with trigger `scheduled` once a day after the set time (default 20:15, local; `settings` table, changed under Accounts & logins). One try a day (`daily_refresh_last`), even if refused; a time saved earlier than now starts tomorrow. Demo databases run with `serve` too, so set their time far off or turn it off.

## Commands

```bash
.venv/bin/python -m pytest tests -q                 # all tests; run before every commit
.venv/bin/python -m portfolio_agent.cli serve       # dashboard on http://127.0.0.1:8765
.venv/bin/python -m portfolio_agent.cli --db /path/demo.db serve   # demo data; set PA_PORT for another port
```

- **API:** every request other than GET needs the header `X-PA-Client: 1`. For example, `PUT /api/logins/{id}` saves a login's rules and `PUT /api/accounts/{id}` saves an account.
- **The owner runs `serve` in their own terminal.** After backend changes, ask them to restart it. A statement read by a server started before the change still uses the old code. Front-end files (`web/static/`) only need a browser reload.
- **`node` is not installed.** Check JavaScript syntax with `osascript -l JavaScript`, or by loading the page in the browser pane and reading the console.
- **Demos:** for UI checks, build a throwaway database with made-up accounts in the scratchpad and preview it on another port (e.g. 8798/8799). Remove any temporary `.claude/launch.json` entry afterwards.

## Design rules that are easy to break

- **The store is append-only and bitemporal.** Snapshots are never rewritten. Each value has an `as_of_datetime` and a `retrieved_at`, and corrections are new rows.
- **Stored values are what the portal shows.** Two adjustments are applied only when values are read, in `store.py` (`_Values`):
  - the debt sign: accounts with `is_liability` count as negative;
  - the part-owned share: accounts held by an entity in `owners` count at the percentage in `owner_shares` effective on that date.

  View Source, the validator (`previous_snapshot` / `_to_snapshot`) and the holdings list use full values. Never fold either adjustment into stored rows.
- **Per-login rules** (`skip_categories`, `liability_categories`, `skip_other_institutions`, `open_account_details`, `not_accounts`) also apply to existing accounts, through `registry.apply_login_rules`.
- **Code reads account numbers, not the model.** They come from each account's details page (`browser/portal.py`) and are matched by link name. They override the model's guess, and the validator rejects one number given to several accounts.
- **Statements:** code reads a one-account statement's number (`statement_guides.statement_number`), overriding the model. `registry.relink_accounts` (moving an account to a newly read number) runs for portal pages only, never for statements: one statement covers one account, so another account with the same name is simply not in it.
- **Balance-only accounts:** an account read with a stated total but no holdings (a card, loan or bank account) gets one holding worth that total, in code (`ingest_graph.balance_holdings`). The missed-account check (`validator.unlisted_accounts`) skips numbers of this login's ignored or closed accounts (`registry.set_aside_last4s`).
- **Signs:** in an asset account each holding keeps its own sign; only liabilities are forced negative (`ingest_graph._snapshot`). A sold option (negative quantity) is valued in code at −(contracts × 100 × price) (`value_sold_options`), whatever the statement prints.
- **Duplicate statements:** a file is ignored only if it was ingested (`statements.ingested`); otherwise it's read again. A re-read with identical values is "unchanged" and adds no row.
- **Sign in with Google** (`sign_in_with = "google"`, `portal._google_login`): the fetcher only presses the site's Google button and picks an account in Google's chooser. It never types into Google's pages (no password, no code, no consent); anything else stops the run with an Inbox question. `accounts.google.com` is allowed only during sign-in (`holder.nav_domains`). These logins run in the installed Google Chrome (`channel="chrome"`, own profile `<institution>-chrome`, `portal.browser_profile`); `open-browser` starts that Chrome as a normal app for the owner's own Google sign-in. Never add anything that hides automation from Google. Passwords are typed only on the login's own domains.
- **Fund values from a portal page:** an account can carry its own `as_of_datetime` (`AccountRows`), used for its snapshot instead of the page's date, so a fund valued at last quarter end isn't rejected by the live-page rule (V13). Guides can add `portal_notes` and a `portal_marker` (read the page right after sign-in when that text shows), e.g. `STRATEGIC_PARTNERS`. A guide's `portal_date_column` (e.g. "As of Date") makes code read each row's date (`statement_guides.row_dates`, `ingest_graph.apply_row_dates`), overriding the model's; dates like `Jun-30-2026` are parsed by `timeutil.parse_date_text`.
- **Per-fund documents** (`document_name` set on a capital browser login, `portal._fetch_fund_documents`): fund names come from the login's `fund_column` (cells under that heading, `COLUMN_JS`), else the local model picks them from link names only; each fund's latest file named like `document_name` is downloaded, one per fund, by clicking the PDF icon in its row (`_pdf_target`), else the row's actions menu → Download/View (`_download_via_menu`), else its checkbox + the page's Download button (`_download_via_checkbox`, PDFs only). A stopped run also saves `stopped.html` (local only) so failures can be diagnosed by structure counts. A same-tab PDF is fetched and the page goes back. `_find_control` prefers a control in the page content over one in a sidebar or header (a fund page's Documents tab, not the sidebar's).
- **Capital statements from a portal's documents page** (only when the login sets a documents tab, `portal._fetch_documents`): after sign-in the fetcher clicks the documents tab and the filter by label (or types the term into the page's search box), then downloads only the rows dated in the newest quarter (`latest_rows`). Downloads come only from the login's domains, a link to another site or with a blocked label is skipped (never clicked), and each file goes through `statements.save_upload` / `read_one`, so duplicates are recognized like uploads.
- **Code sent on request** (`otp_button`, e.g. "Generate New OTP", `portal._code_on_request`): after the username and password, the fetcher presses that button, reads the emailed code from Gmail when set up (`portal._emailed_code`), else asks for it in the Inbox, types it into the form's code box and presses the sign-in button. After any sign-in press, `_wait_past_login` waits up to `LOGIN_WAIT_S` (60 s) for the form to go away, stopping early only when the form shows an error (`LOGIN_ERROR`); a slow portal's status notice isn't a rejection. The form counts as gone once the address changed and no password box shows; read-only or disabled inputs never count as username fields (a profile page's email box). A form with a code box beside the password counts as the login page, not a 2FA page. The code is never traced.
- **Documents tab without a filter:** a "Capital Account Statements" filter or search is used when the page offers one; otherwise the whole list is used; a monthly login downloads only the newest month's rows (`latest_rows(monthly=True)`), a quarterly one the newest quarter's. The documents tab may instead be the page's `https://` address (opened directly after sign-in, only on the login's domains). Clicking the documents tab goes through `_click_and_wait`: it first waits for the address to stop changing (`_settled_url`, sign-in redirects) and for a menu link's address to be filled in (Tattva's NAV link points back at the current page until a script sets it; up to 15 s), then waits until the browser is on the link's page; if it lands elsewhere it opens the link's own address (same site only), tracing each `opened` URL (network-quiet alone passed too early on an older portal), and download links are looked for for up to 10 s. Links come first from a table column headed "Download" (`_column_links`: the icon in each row's cell, so icon-only links work and a page-wide Download button used with checkboxes is never picked), else from links named download/view/pdf.
- **CAPTCHAs are for the owner only** (`portal._wait_for_person`): the run brings its window to the front, posts an Inbox note and waits for the owner to solve it. Never click, type into, or otherwise work around a CAPTCHA in code.
- **Captured page text** (`portal._capture_page`) is the visible text plus each table again as rows (`cell | cell`, cell tooltips included) and values shown in fields and dropdowns (`STRUCTURE_JS`). Password, username, email, code and card fields are never included; keep that filter when changing it.
- **Saved files (View Source, statements)** are served with `nosniff`, and every type except PDF also with `Content-Security-Policy: sandbox` (`web/app.py` `_file_headers`); portal HTML is shown as text. PDFs get no sandbox because Chrome's PDF viewer shows a blank page under one.
- **Image-only PDFs** go through local OCR (`documents.ocr_pdf`, macOS Vision via `portfolio_agent/ocr/pdf_ocr.swift`, built to `~/.portfolio-agent/bin`). Never use a cloud OCR service. Tests stand in for it; they don't run Swift.
- **Parallel refreshes:** logins at the same institution share a browser profile, so they never run at the same time (`store.busy_login_ids`). The model is used by one run at a time (`llm.py`).
