# 4.1 Capstone Checkpoint: Personal Portfolio Agent (Tree of Thought)

## Topics to be addressed

**Q1.** Decide whether Tree of Thought (ToT) reasoning is appropriate
for the agent, and whether it would improve or hinder the design.

**Q3.** Because ToT is not used: why it is not appropriate, showing it
was considered and rejected on purpose; and the reasoning approach that
fits the agent better, with why.

## A1. ToT is not appropriate for the agent now

**Decision: do not build ToT now. Keep the bounded ReAct loop with
deterministic validation and my review, and build ToT only if real
failures show a need for it.** I looked at each part of the agent to see
where ToT could fit:

| Part of the agent | ToT? | Why |
|----|----|----|
| Interpreting a statement the validator rejected | Possible, unproven | A rejected statement may have several plausible readings (wrong field, wrong column, units, wrong period, or a real change), and each can be tested with arithmetic. But I have not yet seen how often this happens, or whether these errors are truly ambiguous. |
| Portal navigation and login | No, it would hinder | Branches would be real actions on a live site. Trying several login routes can trigger lockouts and floods of 2FA codes, and nothing can be rolled back. |
| Routine nightly extraction | No, it would hinder | Most extractions should pass validation the first time. A tree on every account would multiply model calls for no gain. |
| Q&A and change explanations | No, not needed | Numbers come from exact store queries and the calculator, and reasons come from retrieval (3.1). There is little to search over. |

**Improve or hinder?** Today ToT would hinder the design. It adds model
calls, thresholds to tune and components to test, while the one benefit
it might bring has not been observed.

## A3.1 Why ToT is not appropriate

This is a deliberate decision, not an omission. The only credible place
for ToT is interpreting a rejected capital statement, and I chose not to
build it there yet for four reasons.

- **No evidence of the failure yet.** I do not know how often statements
  will be misread, or which kinds of errors will occur. Many are likely
  to be simple and repeatable, like reading "Total commitment" as the
  value. One approved correction fixes that kind of error permanently; a
  search tree is not needed.

- **The risk is already contained.** ToT would protect against a misread
  becoming a stored value. The validator already prevents that: a
  reading that fails the roll-forward, continuity or date checks is
  never stored, and it goes to my review queue instead.

- **It cannot be tuned without real data.** A tree needs scoring
  weights, pruning thresholds and tie rules. Set before any real
  failures have been seen, they would be guesses, and a badly tuned tree
  can prune the right answer.

- **It adds cost and complexity.** Each tree means many extra model
  calls on a local model, and more parts to test, debug and explain in
  the final demonstration.

## A3.2 The approach that fits: ReAct with validation in code and human review

The agent keeps the reasoning approach from 2.1: a bounded ReAct loop
for each task, deterministic checks before anything is stored, and me as
the final reviewer for anything uncertain. When a statement is rejected:

1.  The fetcher retries once by another route, such as the downloaded
    PDF instead of the web page.

2.  If the validator still rejects it, the item goes to my review queue
    with the evidence and the check that failed.

3.  I fix it, and the fix is saved as a correction. Next quarter,
    retrieval (3.1) brings that correction back before the extractor
    reads the same fund's statement.

This supports the agent's goal, a verifiable record of every value,
better than ToT:

- **One observed step at a time** suits live portals, where an action
  cannot be undone.

- **Numbers are right by checking, not by search.** Code decides whether
  a value is accepted, so better reasoning is not needed to get the
  numbers right.

- **Uncertainty is surfaced, not guessed.** Anything the checks cannot
  confirm reaches me instead of being resolved by a model's best guess.

- **Learning accumulates cheaply.** Each correction prevents the same
  mistake for good, at no extra model cost.

- **Cost is predictable.** One loop per account, with a fixed step
  budget.

## A3.3 When ToT would be reconsidered

The review queue gives me the evidence to revisit this decision. Every
rejection will be tagged with its cause: wrong field, wrong column,
units, wrong period, real change, or parsing error. I would build ToT
if, over about six months of real runs, either of these is true:

- Rejections where the statement could be read several ways happen
  several times.

- The same kind of error keeps coming back even after I have approved a
  correction for it.

If triggered, ToT would be added only as a fallback for rejected
statements. It would use beam search with a beam of 2 and a depth limit
of 3. Checks that use only the current statement (roll-forward,
traceability, date) could prune a reading, and checks against history
and the fund letter would rank the survivors. If the top two readings
disagreed, both would go to my review queue. The thresholds would be
tuned on the logged rejections, which is exactly the data I do not have
today.
