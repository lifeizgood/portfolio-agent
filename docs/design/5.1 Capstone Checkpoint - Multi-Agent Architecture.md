# 5.1 Capstone Checkpoint: Personal Portfolio Agent (Multi-Agent Architecture)

## Problem and why it needs several agents

The Personal Portfolio Agent builds one verified, bitemporal history of
every account I hold, refreshed each night, and explains changes in net
worth during the day. It is read-only and never trades or changes
settings. The demo uses synthetic accounts and documents only.

A single agent would do this badly for three reasons. **The tasks need
different tools and permissions.** Logging into a portal needs the
browser and the 2FA reader; reading a capital statement needs the
mailbox and PDF tools; answering a question needs only the store and the
calculator. One agent holding all of them would let a malicious
instruction in an email reach every tool. **The work is independent
across institutions.** A broken login at one portal should not stop a
private fund's statement from being read. **The context would not
hold.** One agent carrying ten portals' pages and statements at once
would lose track of which number came from where, the failure 2.1 was
designed to prevent.

## Agents, roles and responsibilities

The system has six agent roles. Validation, pricing, arithmetic, storage
and credentials need no judgment and stay in deterministic code.

|  |  |  |  |
|----|----|----|----|
| **Agent** | **Responsibility** | **Tools** | **Hands off to/ Output passed to** |
| **Orchestrator** (supervisor) | Reads the account registry, selects the accounts due tonight by cadence, dispatches workers, routes failures and joins results. Planning follows registry rules; the LLM re-plans only when a branch fails unexpectedly. | Registry, run state | Run plan; run status |
| **Portal fetcher** (one instance per institution) | Bounded ReAct loop: log in, navigate, capture the holdings page or download the statement, guided by that portal's playbook. | Browser, Auth tool, playbook retrieval | Evidence bundle |
| **Statement fetcher** | Finds capital statements in the labeled mail folder, finds the separate password email and opens the PDF. | Mail reader, PDF tools | Evidence bundle |
| **Extractor** | Turns evidence into rows (holding, quantity, value, as-of date), after retrieving my approved corrections for that fund. | Document parser, corrections retrieval | Candidate snapshot |
| **Research agent** | Collects published ratings and notes for public holdings and flags any holding not rated Buy, with source and date. | Ratings tool, research-note retrieval | Rating flags |
| **Analyst** (reporter and Q&A) | Writes the morning summary and answers questions, citing numbers from the store and reasons from retrieved letters (3.1). | Store queries, calculator, quotes, retrieval | Summary; cited answers |

**How I arrived at six.** I placed a boundary wherever the tools,
permissions or failure behavior change, and nowhere else. Fetching is
separate from extracting because fetching acts on live sites and
extracting only reads a saved file: the extractor can be re-run on
stored evidence without logging in again, and it never holds browser
access. I merged the reporter and the Q&A agent, because they use
identical tools and a handoff between them would add latency and no
capability. I rejected two more agents because returns diminish. An LLM
critic checking the extractor would share its blind spots; the code
validator is deterministic, testable and free. A planner, researcher and
writer split for Q&A would add handoffs to answers that are short and
grounded in exact queries.

## Coordination strategy: a supervisor graph (hybrid)

A LangGraph graph, with the orchestrator as supervisor, combines
parallel, sequential and iterative patterns:

- **Parallel fan-out.** The orchestrator starts one branch per due
  account, at most three at a time.

- **Sequential within a branch.** Fetch, extract, validate, in order,
  like an assembly line.

- **One bounded loop.** If the validator rejects a snapshot, the branch
  retries once by another route (the downloaded PDF instead of the web
  page) with the failed check attached. A second rejection sends the
  item to my review queue with its evidence.

- **Join, then report.** When every branch has finished or timed out,
  the research agent runs, then the analyst writes the morning summary
  from the store.

During the day the analyst runs alone, on demand, with read-only access
to the store. A purely sequential design would make each night as slow
as the sum of all portals, and one stuck login would block the rest. A
free-form network of agents calling each other would be hard to test and
debug.

## Communication

- **One-way, typed handoffs by default.** Each agent writes a structured
  message to the shared graph state (account ID, evidence file path,
  rows, as-of and retrieved-at dates, status) and the next node reads
  it. Secrets never appear in messages.

- **Two-way where validation needs it.** The validator returns the
  specific check that failed, so the retry is targeted rather than a
  repeat. I am the other two-way channel: corrections I approve in the
  review queue are indexed and read by the extractor the next quarter.

- **No brainstorming between agents.** Values are accepted because code
  checks pass, not because several models agree, which matches the
  decision in 4.1 not to use Tree of Thought.

- **All traffic goes through the supervisor's state.** No agent calls
  another directly, so every handoff is logged and replayable. Only the
  extractor reads raw page or PDF text, and it has no tools that act.

## Trade-offs considered

|  |  |  |  |
|----|----|----|----|
| **Decision** | **Benefit** | **Cost** | **How the cost is managed** |
| One validation retry | Recovers from route-specific errors such as a badly rendered page | A second fetch, on failures only | Capped at one; everything else goes to me |
| Parallel fetchers | Night run takes about as long as the slowest portal | Two SMS codes arriving together could be mixed up; more load on the local model | At most three branches; SMS logins take a lock so only one code is expected at a time |
| Code validator instead of an LLM critic | Deterministic, testable, no extra model calls | Catches only what it was written to check | Unexplained large moves are flagged for review |
| Central supervisor | One place for plan, state and logs | Single point of failure | Graph checkpointing: a crashed run resumes at the last finished node |

## Why the architecture scales

Adding an institution means a registry row and a playbook: more fetcher
instances, but no new agent role and no change to the graph. Failures
stay local: a broken portal fails only its branch, and the dashboard
marks that account stale instead of dropping it from net worth. Cost is
predictable, since each fetcher has a step budget of about 25 actions
and private funds are fetched only when a quarterly statement is due.
New capabilities, such as a tax-lot agent that reads the store, attach
as new nodes without touching the fetchers. Because handoffs are typed
messages, each agent can be tested alone on saved, synthetic evidence.
