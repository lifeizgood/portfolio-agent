## A1. Retrieval is required, but only for text

Values and changes stay in the exact, bitemporal portfolio store. Two
kinds of retrieval is required

1.  Retrieval from private sources supplies the explanations, procedures
    and context that live in documents, and anything retrieved is
    checked against the store before the agent uses it.

2.  Retrieval from public sources is used for explanations, and context
    explaining why value of public equities is changing.

## Why is retrieval required?

The agent answers two kinds of questions, and they need different
mechanisms.

- **"What is it worth, and how did it change?"** This is an exact lookup
  in the portfolio store. Similarity search is the wrong tool: a value
  from a nearby date or a similar account is a wrong value. No
  retrieval.

- **"Why did it change, what does the statement say, and how do I get
  it?"** These answers live in text: quarterly investor letters and
  capital statement notes, published research notes, portal playbooks
  and corrections I have approved. Across many funds and years this is
  hundreds of documents, too many for one prompt, and it grows every
  quarter. Retrieval.

Without retrieval, the agent can report that a fund fell in value, but
not why. An LLM asked "why" with no source tends to supply a plausible
guess. Checkpoint 2.1 was designed to remove exactly that failure.

## A2. How retrieval is integrated?

The external data sources are documents the agent already collects:
investor letters and capital statements (from the labeled email folder
and portal downloads) and published research notes (from the research
data feed). Two internal sources use the same index: per-portal
playbooks and approved corrections.

1.  **Ingest.** The statement fetcher and research agent save each new
    document with its metadata: account, fund, document type, as-of
    date, date received and source.

2.  **Parse.** Tables go to the extractor, and their numbers go to the
    store after validation. Narrative text goes to the index.

3.  **Chunk and embed.** A local embedding model embeds the text, and
    the index sits in the same encrypted local store, so nothing leaves
    my Mac.

4.  **Search.** Filter by metadata first, then rank by a combined
    semantic and keyword score, and keep only results above a minimum
    score.

5.  **Answer.** The LLM writes only from the retrieved chunks and cites
    each one. Numbers come from the store, and any percentage in a
    retrieved chunk is compared with the store's change.

| Agent | Retrieves | Used for |
|----|----|----|
| Reporter and Q&A | Investor letters, statement notes | Explaining why a value changed |
| Research agent | Research notes | Why a holding is rated below Buy |
| Portal fetchers | Playbook for that portal | Finding statements at the start of a run |
| Extractor | Approved corrections | Avoiding a mistake I already fixed, e.g. reading "Total commitment" as the value |

## A4. Key retrieval design choices

| Choice | Decision | Why |
|----|----|----|
| Data sources | Investor letters, capital statement notes and research notes; plus playbooks and corrections | Where "why" and "how" answers live, and the agent already collects them |
| Segmentation | Split by section heading. Tables go to the extractor, not the index. Long sections are split by sentence (about 300–400 tokens) with a one-sentence overlap | A section usually covers one topic; tables are numbers and belong in the store |
| Chunk header | Each chunk is embedded with the fund name, document title and section | A short chunk such as "NAV decreased 5.8%" otherwise loses which fund it describes |
| Metadata | Account, fund, document type, as-of date, date received, source, page | Enables filters and citations |
| Embeddings | Local sentence-embedding model | Private documents stay on my Mac |
| Ranking | Metadata filter first, then 0.7 × semantic + 0.3 × keyword score | Keywords keep tickers and fund names exact, where embeddings blur them |
| Results | 8 candidates; the top 3 scoring at least 0.55 go to the LLM; none above 0.55 means no answer | Enough to explain a quarter without diluting it with weak matches |
| Refresh | New documents are indexed nightly; old ones are kept with their as-of dates | Matches the bitemporal history |

## A5. Failure mode: right fund, wrong quarter

Letters from the same fund read alike from quarter to quarter, and
letters from different funds share words such as "NAV decreased" and
"markdown." Similarity alone ranks them close together. An answer built
from those would explain a June drop with March text, or with another
fund's markdown.

The design manages this in four ways:

- **Filters before similarity.** The account must match and the as-of
  date must fall in the period asked about. With filters on, all three
  results come from the correct Q2 letter.

- **Cross-check against the store.** Any percentage in the retrieved
  text is compared with the store's change. In the unfiltered run the
  check reports "source +0.3%, store −6.0%, mismatch, flag for review."

- **Visible citations.** Each claim shows its fund and as-of date, so I
  can see a wrong quarter immediately.

- **Abstain.** If no document for the period scores above the threshold,
  the agent says so instead of explaining. In the demo, a Q3 question
  gets "latest letter on file is as of Jun 30."

Retrieved text is also treated as data, never as instructions, since
emails and PDFs can contain text written to mislead an agent.
