# 6.1 Capstone Checkpoint: Portfolio Agent Safety and Intervention Plan

## What the agent does and where it can go wrong

The Personal Portfolio Agent logs into my financial portals and mailbox
each night, extracts holdings and values, and builds one verified,
bitemporal history of my net worth. During the day it explains changes
and answers questions. This plan covers the controls around the 5.1
multi-agent design. The demo and tests use synthetic accounts and
documents only.

|  |  |  |
|----|----|----|
| **Risk** | **Example in this workflow** | **Harm** |
| Wrong value stored | The extractor reads "Total commitment" as NAV, or 1,032,000 as 1,302,000 | A false history that later checks compare against |
| Wrong period | A June 30 value received in October is treated as a change this week | Misleading explanations of net worth |
| Unintended action on a live account | A fetcher clicks a transfer or settings button | Real financial loss; cannot be undone |
| Account lockout | Repeated login attempts or a flood of 2FA codes | Locked out of my own account |
| Prompt injection | An email or PDF contains text telling the agent to forward statements | Data leak, or tools misused |
| Secret exposure | A password or 2FA code reaches the model, a log or a prompt | Account compromise |
| Ungrounded answer | "Why is the fund down?" answered with a guess such as "market conditions" | Confident, wrong advice to myself |
| Silent staleness | A broken portal stops updating and its old value is shown as current | Net worth looks right but is not |

## Guardrails

- **Tool access limits.** Every tool is read-only. The browser is
  restricted to the portal domains in the account registry, and it may
  submit only the login form; clicks on controls labeled transfer,
  trade, withdraw, order, delete or settings are blocked in code.
  Credentials are filled from Keychain by the Auth tool and never pass
  through the model.

- **Input checks.** The mail reader opens one labeled folder and only
  messages from full sender addresses in the registry. Page, email and
  PDF text is passed to the model as data, never as instructions, and
  only the extractor reads it; the extractor has no tools that act. Only
  I can change the registry.

- **Runtime limits.** Each fetcher has a budget of about 25 steps and a
  time limit, at most two login attempts per portal per night, and one
  SMS code expected at a time. A CAPTCHA, an unknown 2FA prompt or an
  unexpected domain stops the branch.

- **Output constraints and source verification.** A value is written to
  the store only by code, and only after the validator passes: rows sum
  to the stated total, quantity × price matches the market feed, the
  as-of date is valid and not earlier than the last accepted value,
  statements roll forward, and the change from last time is explainable.
  Q&A answers must cite store numbers and a retrieved document, any
  percentage in a document is cross-checked against the store, and the
  analyst abstains when no source scores above the threshold (3.1).

- **Runtime monitoring.** Every run keeps a trace of actions and
  evidence. A completeness check marks any account without a value
  inside its cadence as stale, and blocked actions or off-allowlist
  navigation raise an alert in the morning summary.

## Evaluation metrics

Measured on a labeled synthetic test set before each change and on live
runs after. Targets will be tuned on real data.

|  |  |  |
|----|----|----|
| **Area** | **Metric** | **Target** |
| Correctness | Field accuracy of extracted value and as-of date on the test set | ≥ 99% |
| Correctness | Escape rate: accepted values I later correct | 0 |
| Groundedness | Q&A claims with a citation; citations that support the claim (spot-checked) | 100%; ≥ 95% |
| Calibration | Abstains when no source exists; answers when one does | 100%; ≥ 90% |
| Safety | Injection test cases that trigger any tool call; secrets in logs or prompts; lockouts | 0; 0; 0 |
| Reliability | Coverage: active accounts with an accepted value inside their cadence | ≥ 95% |
| Fallback success | First-time rejections fixed by the single retry | Tracked; rising |
| Escalation rate | Share of values sent to my review queue | 5–15% |
| Latency and cost | Nightly run finished by 7 a.m.; Q&A answer time; my review time per week | Yes; \< 30 s; \< 20 min |

The escalation rate has a band: above it the validator is too strict;
below it, checks may be letting errors through.

## When a human must decide

The agent proceeds alone only when the work is routine and verified: a
value that passes every check, a single retry by another route, or
repricing public holdings. It defers to me when any of these holds:

- **Uncertain data.** The validator rejects a value twice, or a change
  exceeds the continuity threshold with no matching market move. The
  value is held, with its evidence, and not stored until I approve.

- **First of its kind.** The first value for a new account, or the first
  run after a portal's playbook changed.

- **Security or policy prompts.** A CAPTCHA, a new 2FA method, a
  security question, a device-verification or terms-of-service page, or
  any page asking for an action. The branch stops and asks me.

- **Changes to trust.** A new statement sender or a new portal address.
  The agent can suggest the change; only I can approve it.

- **Blocked behavior.** Any blocked click or off-allowlist navigation
  stops that branch and alerts me.

- **Weak evidence for an answer.** No source above the threshold, or a
  cross-check mismatch: the analyst says so instead of explaining.

- **Repeated failure.** The same portal fails three nights in a row: the
  playbook likely needs updating.

## How the parts work together

The plan works in layers. Guardrails prevent what must never happen (an
action on an account, a leaked secret). The validator and monitoring
detect what can still go wrong (a misread value, a stale account). Human
review decides the cases code cannot settle. Each decision I make
becomes a correction the extractor retrieves next time. The metrics
measure the guardrails as well as the agent: the escape rate tests the
validator, the escalation rate tests its thresholds, and the injection
set tests the input boundary.

## Trade-offs

- **Autonomy against oversight.** Holding every unusual value for me
  protects the history but costs review time.

- **Strictness against completeness.** Stopping at a CAPTCHA or an
  unknown prompt leaves some accounts stale for a night. A stale value
  that is labeled as stale is safer than a guessed one.

- **Read-only against convenience.** The agent cannot accept a portal's
  new terms or download a statement behind an extra confirmation. I do
  those few steps myself.

- **Local model against capability.** A local model is weaker than a
  hosted one, but my statements never leave my Mac, and code checks
  decide what is accepted.

- **Abstaining against helpfulness.** A wrong explanation is worse than
  none.

## Path to dependable real-world use

The agent goes live in one week, in stages gated on the targets above:

- **Days 1–2: synthetic test set.** It must meet the correctness,
  calibration and safety targets, or go-live moves.

- **Days 3–6: shadow mode.** The agent runs nightly on my real accounts;
  I check each value against the portal and nothing is trusted. Private
  funds are back-tested on the last two or three statements already in
  my mailbox, since no new quarter arrives this week.

- **Day 7: live for nightly accounts.** Accounts with four clean shadow
  nights go live. Private funds go live in supervised mode: every new
  value waits for my approval until the first live quarterly statement
  passes the checks.

An account that fails repeatedly returns to shadow mode. A single switch
stops all fetchers, and because the agent is read-only, stopping it
never leaves an account half-changed.
