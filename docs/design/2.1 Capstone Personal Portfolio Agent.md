# **1.1 Capstone Checkpoint: Personal Portfolio Agent** {#1.1-capstone-checkpoint:-personal-portfolio-agent}

## **Summary** {#summary}

The Personal Portfolio Agent is a locally run, read-only multi-agent system. Each night it consolidates holdings and values from every financial account I hold into one history. It logs into heterogeneous portals (some behind two-factor authentication), reads capital statements from portals and email, and records each value with both the date it was retrieved and the date it is valid as of. During the day it re-prices publicly traded holdings live, explains changes in net worth, and flags holdings whose published research rating is not Buy.

The agent never trades, transfers or changes account settings. Its job is to see, record, verify and explain.

## **Problem and intended user** {#problem-and-intended-user}

An individual investor with assets spread across many institutions has no single, trustworthy view of total net worth or how it has changed over time. Every number exists somewhere, but in different places, formats and levels of staleness.

**Intended user:** one individual investor (me), managing a mix of brokerage, wealth-management, retirement and private or alternative investment accounts. The user is technical enough to run software locally but does not want to log into each portal by hand.

**What makes the problem hard:**

* **Many portals, no common format.** Each institution (for example, Rockefeller Digital. Schwab, PE portals) lays out holdings differently and may also infrequently change interface.  
* **Two-factor authentication.** Some portals send a code by SMS, others by email. There may be some using authenticator app too, but I can’t remember specific example at this time.   
* **Mixed update cadences.** Public securities reprice continuously when markets are opn. Private and alternative investments update quarterly, often 2–4 months after the quarter ends.   
* **Values arrive in different forms.** Some appear on a web page. Others exist only as a Capital Statement PDF, downloaded from a portal or sent as an email attachment.  
* **Two dates per value.** A value retrieved in October may describe the value asof June 30\. Without storing both dates, a late quarterly data retrieved looks like a change that happened today.

**Goal:** a daily-updated, verifiable record of every holding by source and account name, and its value, a chart of net worth over time, with ability to slice and dice. It should also be able to give plain-language answers to questions such as 

1. Why is my net worth down?  
2. What investment has the best CAGR over last “n” years, or over “m” months? 

## **Why a single prompt or stand-alone LLM is insufficient?** {#why-a-single-prompt-or-stand-alone-llm-is-insufficient?}

A language model on its own cannot see my accounts, act on them, remember past values or check its own numbers. This problem needs all four.

| Requirement | Why one prompt fails | What the agent adds |
| :---- | :---- | :---- |
| Live, private data | The model has no access to my portals, email or current prices | Tools for browsing, mailbox reading, PDF parsing and market quotes |
| Many dependent steps | Login, 2FA, navigation, download and extraction must happen in order, and each depends on the last | A reasoning loop (ReAct) that observes each result before choosing the next action |
| Unpredictable environment | Pages (user interface, layout) change, sessions expire, statements arrive late | Recovery: retry, try another route, or escalate to me |
| History over time | A prompt forgets everything after it ends | A bitemporal database (as-of as well was  retrieved-at time) plus retrievable per-institution playbooks |
| Correctness | A model can misread or invent a number with full confidence | Validation in code, independent cross-checks and saved evidence for every value (Is this enough? How do I put in checks that the data extracted/ imported in correct?) |
| Unattended schedule | A chat only runs when someone types | A nightly scheduler and a morning queue for items that need me |

The reverse also holds: a plain script with hard-coded selectors would break whenever a portal's layout changes, and cannot read varied statement PDFs or answer open questions. The design gives the LLM the parts that need judgment (understanding pages and documents, reconciling values, explaining changes) and leaves arithmetic, credentials and storage to deterministic code.

## **Environment** {#environment}

The agent runs on my MacBook. It reaches outward to financial portals, my mailbox (on my browser), my synced text messages and public market data, and inward to a local database and credential store.

| Element | What it is | How the agent touches it | Access level |
| :---- | :---- | :---- | :---- |
| Financial portals | Brokerage (Schwab), wealth-management (e.g. Rockefeller Digital), retirement and private-fund (Star Mountain) portals | Sandboxed browser with a persistent profile per institution; reads pages and downloads statements | Read-only; domain allowlist |
| Institution APIs and aggregators | Broker APIs, OFX or an aggregator where available.  | Preferred over browsing when offered (Should I try this, or just go with browser logins) | Read-only scopes |
| Email | Capital Statements sent as attachments; the pdfs sometimes need decryption code sent as separate email | Reads only one labeled folder, by filter on known senders (Trying to reduce the scope of the Agent) | Read-only (e.g. Gmail readonly scope or IMAP) |
| Text messages | SMS 2FA codes synced from iPhone to the Mac's Messages database | A code-only reader in plain code, never exposed to the LLM (Not sure if I can achieve this) | Read one message from a known sender in a short window. It may not be possible to identify the senders as “known” (eg if the sending number changes), so at a minimum read only the messages received within a short window of attempting login |
| Market data | Live and end-of-day prices for public securities | Quote tool for nightly pricing and intraday views. This data would likely be available directly from the  | Public, read-only |
| Research data | Published analyst ratings and research summaries | Ratings tool; reports source, date and coverage | Public or licensed, read-only |
| Credential store | macOS Keychain (or a password manager CLI) | Tool layer fills login fields directly; the LLM never sees secrets | Local only |
| Local database | Encrypted store of snapshots, documents, evidence and playbooks | Read and write by tools only | Local only |
| The user | Me | Approves 2FA when needed, reviews flagged values, asks questions | Human in the loop |

The LLM itself runs locally, so page text, statements and holdings stay on the machine.

## **Agent architecture** {#agent-architecture}

The system is an orchestrator that dispatches specialized agents, with every value passing through one extractor and one validator before it is stored.

Portal fetchers run in parallel, one per institution. All agents call tools through a read-only tool layer that holds credentials, the 2FA code reader, the sandboxed browser and the mail reader; the LLM never touches secrets directly.

# **2.1 Capstone Checkpoint: Personal Portfolio Agent** {#2.1-capstone-checkpoint:-personal-portfolio-agent}

The sections above describe what the agent does and why one prompt cannot do it. The sections below describe how it works: each agent runs a bounded ReAct loop that ends in a verification step, memory is split into a per-run working memory and a long-term bitemporal store, and every external action goes through read-only tools.

One principle runs through the design: the LLM decides what to do next and interprets what it sees; deterministic code does the arithmetic, handles credentials and writes to storage. A value only becomes part of my history after code has checked it.

## **Reasoning loop** {#reasoning-loop}

The agent uses two levels of reasoning: the orchestrator plans, and each worker agent runs a ReAct loop (Thought → Action → Observation) that must pass a verification step before it can finish.

**Planning level (orchestrator).** Each night the orchestrator reads the account registry (see Memory) and the date each account last produced a valid value. It decides which accounts need a fetch tonight (all public holdings; private funds only when a new quarter's statement is due) and dispatches one portal fetcher per institution, plus the statement fetcher and market data agent.

**Acting level (ReAct per fetcher).** The fetcher's goal is narrow: return this account's holdings and values, with the date they are valid as of. Each Thought states what the agent believes about the current state and what it needs next. The Action is one tool call. The Observation is the tool's result, which becomes the input to the next Thought. A typical run for a brokerage account:

1. **Thought:** The playbook says positions are under Accounts → Positions; my saved session may still be valid. **Action:** open the positions page.

2. **Observation:** a login page appears. **Thought:** the session expired, so I must log in. **Action:** ask the Auth tool to sign in (it fills credentials from Keychain; I never see them).

3. **Observation:** an SMS code prompt. **Action:** ask the Auth tool to enter the code it reads from Messages.

4. **Observation:** the positions table, but with a column the playbook does not mention. **Thought:** the layout changed; extraction should rely on column headers, not positions. **Action:** send the table to the extractor.

5. **Observation:** rows extracted. **Action:** send them to the validator.

6. **Observation:** checks pass. **Thought:** goal met. Submit the snapshot and record the new column in the playbook.

**How observations change the next decision.** Every observation falls into one of three cases:

* **As expected:** continue with the playbook's next step.

* **Unexpected but recoverable** (expired session, changed layout, slow page): the agent re-plans. It logs in again, finds the table another way, or tries an alternate route such as downloading the CSV or statement PDF.

* **Validation failed or budget spent:** stop, save the evidence (screenshot, extracted rows, which check failed) and put the item in my morning review queue. The agent never guesses a value to finish.

**Verification step.** The validator answers the question raised earlier in this document about how to know extracted data is correct. It runs in code, and a snapshot is accepted only if all checks pass:

* Holding rows sum to the account total shown on the page or statement.

* Quantity × price ≈ market value for each public holding, and the price is close to the market data feed for that date.

* The as-of date is not in the future and not earlier than the last accepted value for that account.

* The change from the last snapshot is explainable: a large move with no matching market move is flagged rather than accepted.

**Guardrails on the loop.** Each fetcher has a step budget (starting at about 25 actions, to be tuned in testing) and a time limit. The tool layer only offers read-only actions, so no chain of reasoning can lead to a trade or a settings change.

The daytime Q\&A agent uses the same loop with different tools. For "Why is my net worth down?" it queries the store, calls the calculation tool, checks live quotes if markets are open, and only then writes an answer that cites the numbers it retrieved.

## **Memory** {#memory}

The task needs both kinds of memory: short-term memory to finish one account's run, and long-term memory because the product is a history of values over months and years.

| Memory | What it holds | Written when | Read when | Why it is needed |
| :---- | :---- | :---- | :---- | :---- |
| Working memory (short-term) | The current run's thoughts, actions and observations; session state; extracted rows awaiting validation | Each loop step | Each next Thought | Login, 2FA, navigation and extraction depend on what just happened |
| Conversation context (short-term) | The current Q\&A thread | Each question | Follow-up questions | "What about just the private funds?" only makes sense after the first answer |
| Portfolio store (long-term, factual) | Every accepted value with account, holding, as-of date, retrieved-at date, source and evidence link | Only after the validator accepts | Continuity checks, net worth charts, change explanations, CAGR | Without it each run starts blind and nothing can be compared over time |
| Playbooks (long-term, procedural) | Per institution: login route, 2FA method, where holdings live, known layout quirks | After a successful run that learned something new | At the start of each fetcher's run | Saves steps and lets the agent notice when a portal has changed |
| Corrections and documents (long-term, retrieved) | Values I corrected in review and why; statements; research notes | After my review; when documents arrive | When a similar case comes up | Stops the agent repeating a mistake I already fixed |

Two rules keep memory trustworthy:

* **Numbers are queried, not retrieved by similarity.** Holdings and values live in a structured, bitemporal table queried exactly. The vector store (RAG) is used only for text: playbooks, past corrections, statements and research notes.

* **Only validated values enter long-term memory.** A misread number stays in working memory and the review queue; it never becomes a "fact" that later runs compare against.

Working memory is cleared at the end of each run, except for the evidence trace saved with the value or the flag.

### **Account registry** {#account-registry}

The account registry is the one list of every account the agent covers, and the orchestrator plans each night's run from it. It is long-term configuration memory: I maintain it, and the agents only read it.

| Field | What it records | Used by |
| :---- | :---- | :---- |
| Display name | The name I see in reports, e.g. "Schwab joint brokerage" | Dashboard, morning summary, Q\&A answers |
| Institution and account type | Institution; brokerage, retirement, wealth management or private fund | Grouping on the dashboard; orchestrator cadence |
| Portal URL | The login page for the institution | Portal fetcher; the browser's domain allowlist |
| Login reference | The name of the Keychain item that holds the login, never the password itself | Auth tool, which fills the login so the LLM never sees it |
| 2FA method | SMS, email or authenticator app | Auth tool, to know where the code will arrive |
| Statement sender | The email address capital statements come from | Statement fetcher's mail filter on the labeled folder |
| PDF password source | The sender of the separate password email, or a Keychain item | Statement fetcher, to open encrypted statements |
| Update cadence | Nightly, or quarterly with the usual reporting lag (2–4 months) | Orchestrator scheduling; validator staleness check |
| Status | Active or closed, with the date it closed | Orchestrator; completeness check; history kept for closed accounts |

**How I maintain it.** I add, edit or close accounts from a settings page on the dashboard (or a local config file). Each change is checked in code before it is saved: the Keychain item exists, the portal domain is added to the allowlist, and the statement sender is a full email address.

**Agents can suggest, not change.** If the statement fetcher sees a capital statement from a new sender, or a fetcher finds a portal has moved to a new address, it adds a suggestion to my review queue. The registry only changes when I approve, so a spoofed email cannot redirect the agent.

**Completeness check.** Every active account must have an accepted value within its cadence: a nightly account by the morning, a quarterly fund within its expected lag. An account that misses this is shown as stale on the dashboard rather than silently dropping out of net worth.

## **Tool use** {#tool-use}

Tools give the agent access, fresh facts and exact computation that the model does not have on its own. All tools sit behind the read-only MCP layer shown in the architecture diagram.

| Tool | Used for | Limitation it addresses |
| :---- | :---- | :---- |
| Browser | Reading portal pages, downloading statements | Access: the model cannot see my accounts |
| Auth (Keychain, 2FA reader) | Signing in and entering codes | Security: secrets never pass through the model |
| Mail reader | Capital statements and PDF passwords from one labeled folder | Retrieval: some values exist only as email attachments |
| Document parser | Tables from statement PDFs | Grounding: values come from the document, not the model's guess |
| Market data | End-of-day and live prices | Freshness: the model's knowledge of prices is stale |
| Research ratings | Published analyst ratings with source and date | Retrieval and grounding for the non-Buy flag |
| Portfolio store and calculator | Querying history; returns, CAGR, change attribution | Computation: exact arithmetic over many records |
| Vector store | Playbooks, corrections, statements, notes | Retrieval of relevant past experience |

Every tool returns a structured result with its source. A failure (timeout, page not found, wrong password for a PDF) comes back as an observation the loop can reason about, not a crash.

**Example 1: computation.** For "Which investment has the best CAGR over the last 3 years?", the agent first queries the store for each holding's values by as-of date, then passes them to the calculator. Asking the model to do this arithmetic over hundreds of values, with uneven dates and cash flows, invites small errors that read as plausible answers. The model's job is to pick the right question to compute and explain the result.

**Example 2: retrieval and grounding.** A private fund's value exists only in a quarterly Capital Statement emailed as an encrypted PDF. The statement fetcher finds the email, finds the separate email with the password, and the parser extracts the NAV and its as-of date. Without these tools the agent would have no value at all, or would carry forward an old one as if it were current.

## **Improvement over a prompt-only approach** {#improvement-over-a-prompt-only-approach}

The design resolves a specific failure: a late quarterly value being explained as a change that happened today.

**The failure.** In October, a private credit fund posts its Q2 Capital Statement, valued as of June 30, and the NAV is lower than the Q1 value. A prompt-only assistant, given my current balances and asked "Why is my net worth down this week?", sees a lower number this week and explains it confidently, perhaps blaming market conditions. The explanation is fluent and wrong: nothing happened this week, and the drop belongs to June.

**How the design resolves it.**

* **Memory:** the bitemporal store records the value with as-of June 30 and retrieved-at October, so the history shows the drop in June, not this week.

* **Reasoning loop:** the Q\&A agent separates "values that changed" from "values that arrived late" before it explains anything.

* **Tools:** the calculator splits the week's change into market moves on public holdings and restated private values, so the answer reads: public holdings rose slightly; the decline is a June 30 private fund value received today.

* **Verification:** the continuity check flags the private fund move if it is large, so I see the statement before it shapes my history.

The same structure fixes a second common failure: a misread or invented number. In a prompt-only approach, a model that reads 1,032,000 as 1,302,000 reports it with full confidence. Here, the validator's sum and price checks catch the mismatch, and the value goes to review instead of into my history.

## **Dashboard and reporting** {#dashboard-and-reporting}

A local web dashboard, served only on my Mac, shows aggregate and per-account data for any period I choose. It reads the portfolio store and the account registry; numbers on it are computed in code, and the LLM is used only for the written explanations and Q\&A.

**Period selector.** Presets (1M, 3M, YTD, 1Y, 3Y, All) and a custom date range. The selected period drives every view on the page, including the Q\&A, so "why is it down?" is answered for that period.

**Views.**

* **Summary tiles:** net worth at the end of the period, change over the period, and the number of items that need my review.

* **Net worth over time:** a line for the period, which I can split by account, institution or asset type.

* **What changed this period:** a bridge from the start value to the end value, split into market moves on public holdings, late or restated private values, and other changes such as contributions, withdrawals or unexplained moves.

* **All accounts:** one row per account from the registry, with display name, institution, latest value, its as-of date, its retrieved date, change in the period and a status (OK, stale or needs review). It can be sorted and filtered by institution or type.

* **Account detail:** clicking an account shows its holdings, its value history, its research flags, and the evidence behind each value (the screenshot or statement it came from).

* **Review queue and Q\&A:** flagged values and registry suggestions to approve, and a question box whose answers cite the numbers they used.

**How the period is applied.** Values are placed by their as-of date, not the date they were retrieved, so a Q2 statement received in October appears at June 30\. For each date in the period, the dashboard uses each account's latest accepted value at or before that date. A private fund value carried forward is labeled with its as-of date, so it is never shown as if it were current.

**"As known on" view.** Because the store is bitemporal, the dashboard can also show what I knew on a past date, using only values retrieved by then. This explains why a past month's net worth changed after a late statement arrived.

The reporter agent's morning summary appears at the top of the page, so the dashboard and the summary always show the same numbers.

## **Open questions for later modules** {#open-questions-for-later-modules}

* **APIs or browser?** Where an institution offers a read-only API or aggregator feed, it would replace much of the browser loop and make tool results more reliable. I will test which of my institutions offer one before building their fetchers.

* **SMS code reader.** I still need to confirm the code reader can read only recent messages from the Messages database without exposing other texts to the model.

* **Tuning the loop.** The step budget, the continuity threshold for flagging a move, and how often a playbook is rewritten will be set from test runs rather than fixed now.

* **Dashboard technology.** A small local web app is enough; I will choose the framework when I build it, keeping it on localhost with no external hosting.
