## **Summary**

The Personal Portfolio Agent is a locally run, read-only multi-agent system. Each night it consolidates holdings and values from every financial account I hold into one history. It logs into heterogeneous portals (some behind two-factor authentication), reads capital statements from portals and email, and records each value with both the date it was retrieved and the date it is valid as of. During the day it re-prices publicly traded holdings live, explains changes in net worth, and flags holdings whose published research rating is not Buy.

The agent never trades, transfers or changes account settings. Its job is to see, record, verify and explain.

## **Problem and intended user**

An individual investor with assets spread across many institutions has no single, trustworthy view of total net worth or how it has changed over time. Every number exists somewhere, but in different places, formats and levels of staleness.

**Intended user:** one individual investor (me), managing a mix of brokerage, wealth-management, retirement and private or alternative investment accounts. The user is technical enough to run software locally but does not want to log into each portal by hand.

**What makes the problem hard:**

* **Many portals, no common format.** Each institution (for example, Rockefeller Digital. Schwab, PE portals) lays out holdings differently and may also infrequently change interface.  
* **Two-factor authentication.** Some portals send a code by SMS, others by email. There may be some using authenticator app too, but I can’t remember specific example at this time.   
* **Mixed update cadences.** Public securities reprice continuously when markets are opn. Private and alternative investments update quarterly, often 2–4 months after the quarter ends.   
* **Values arrive in different forms.** Some appear on a web page. Others exist only as a Capital Statement PDF, downloaded from a portal or sent as an email attachment.  
* **Two dates per value.** A value retrieved in October may describe the value asof June 30\. Without storing both dates, a late quarterly data retrieved looks like a change that happened today.

**Goal:** a daily-updated, verifiable record of every holding by source and account name, and its value, a chart of net worth over time, with ability to slice and dice. It should also be able to give plain-language answers to questions such as 

1. Why is my net worth down?  
2. What investment has the best CAGR over last “n” years, or over “m” months? 

## **Why a single prompt or stand-alone LLM is insufficient?**

A language model on its own cannot see my accounts, act on them, remember past values or check its own numbers. This problem needs all four.

| Requirement | Why one prompt fails | What the agent adds |
| :---- | :---- | :---- |
| Live, private data | The model has no access to my portals, email or current prices | Tools for browsing, mailbox reading, PDF parsing and market quotes |
| Many dependent steps | Login, 2FA, navigation, download and extraction must happen in order, and each depends on the last | A reasoning loop (ReAct) that observes each result before choosing the next action |
| Unpredictable environment | Pages (user interface, layout) change, sessions expire, statements arrive late | Recovery: retry, try another route, or escalate to me |
| History over time | A prompt forgets everything after it ends | A bitemporal database (as-of as well was  retrieved-at time) plus retrievable per-institution playbooks |
| Correctness | A model can misread or invent a number with full confidence | Validation in code, independent cross-checks and saved evidence for every value (Is this enough? How do I put in checks that the data extracted/ imported in correct?) |
| Unattended schedule | A chat only runs when someone types | A nightly scheduler and a morning queue for items that need me |

The reverse also holds: a plain script with hard-coded selectors would break whenever a portal's layout changes, and cannot read varied statement PDFs or answer open questions. The design gives the LLM the parts that need judgment (understanding pages and documents, reconciling values, explaining changes) and leaves arithmetic, credentials and storage to deterministic code.

## **Environment**

The agent runs on my MacBook. It reaches outward to financial portals, my mailbox (on my browser), my synced text messages and public market data, and inward to a local database and credential store.

| Element | What it is | How the agent touches it | Access level |
| :---- | :---- | :---- | :---- |
| Financial portals | Brokerage (Schwab), wealth-management (e.g. Rockefeller Digital), retirement and private-fund (Star Mountain) portals | Sandboxed browser with a persistent profile per institution; reads pages and downloads statements | Read-only; domain allowlist |
| Institution APIs and aggregators | Broker APIs, OFX or an aggregator where available.  | Preferred over browsing when offered (Should I try this, or just go with browser logins) | Read-only scopes |
| Email | Capital Statements sent as attachments; the pdfs sometimes need decryption code sent as separate email | Reads only one labeled folder, by filter on known senders (Trying to reduce the scope of the Agent) | Read-only (e.g. Gmail readonly scope or IMAP) |
| Text messages | SMS 2FA codes synced from iPhone to the Mac's Messages database | A code-only reader in plain code, never exposed to the LLM (Not sure if I can achieve this) | Read one message from a known sender in a short window. It may not be possible to identify the senders as “known” (eg if the sending number changes), so at a minimum read only the messages received within a short window of attempting login |
| Market data | Live and end-of-day prices for public securities | Quote tool for nightly pricing and intraday views. This data would likely be available directly from the  | Public, read-only |
| Research data | Published analyst ratings and research summaries | Ratings tool; reports source, date and coverage | Public or licensed, read-only |
| Credential store | macOS Keychain (or a password manager CLI) | Tool layer fills login fields directly; the LLM never sees secrets | Local only |
| Local database | Encrypted store of snapshots, documents, evidence and playbooks | Read and write by tools only | Local only |
| The user | Me | Approves 2FA when needed, reviews flagged values, asks questions | Human in the loop |

The LLM itself runs locally, so page text, statements and holdings stay on the machine.

## **Agent architecture**

The system is an orchestrator that dispatches specialized agents, with every value passing through one extractor and one validator before it is stored.

Portal fetchers run in parallel, one per institution. All agents call tools through a read-only tool layer that holds credentials, the 2FA code reader, the sandboxed browser and the mail reader; the LLM never touches secrets directly.
